# Shared L2 控制面优化压测（2026-10-29）

本轮完成吞吐约 **2.93–2.96 亿 input TPM**，没有达到接近 4 亿。
提高发入压力主要增加 Prefill 排队。manager 的常态 CPU 已明显降低，
但不能据此断言所有共享 L2 开销已消失，或定位到某个 GPU kernel。

## 配置与测量口径

- TY18：四 DEP2 Prefill，八 DP worker，统一 256 GiB shared L2；代码 `f15d7e3ef2`。
- TY19：复用 service-r22 DEP8 Decode、Dynamo；隔离 Gateway 渠道 16。
- 正常 CUDA Graph、APC、NVFP4 KV、MXFP4 indexer、MegaMoE/Mega Attention、DSpark5。
- 相同历史合成输入：32k–500k，20 个重复前缀、独立尾部；约 90.014% token 命中。
- 输出上限 8192，自然输出；两客户端各 3 CPU、1024 在途上限。
- 表中完成吞吐及 P99 均为**该档发压结束前 60 秒**，包含缓存输入 token。
- r2 已完整收集 usage，可计算实际发入。r3/r4 根据用户指令，在阶段结束直接 kill
  客户端，不等排空；其发入量由已发送请求数和数据集标称长度估计，不冒充完整 usage。
- r4 未达到实际 4 亿发入：在途上限触发背压，标称长度折算约 3.69 亿。
  r4 紧接 r3，服务端仍可能执行上一档被截断的请求，因此不是独立空队列容量测试。

不能把被 kill 的在途请求遗漏后宣称高档全请求成功或无长尾风险。

| 运行 | manager CPU 中位数 | P95 | 最大采样 |
| --- | ---: | ---: | ---: |
| r2 | 14.78% | 65.03% | 78.79% |
| r3 | 15.32% | 62.99% | 109.93% |

Docker 100% 约等于一个逻辑核。r3 有短时满核采样，不能写成从未饱和。
但高压阶段 P 八卡多次采样全部 100% 利用率，P 队列显著增长，D 队列较小；
证据指向剩余限制主要在 P 执行路径。仅凭利用率无法区分 GPU 计算、内存访问、
Engram 访问或通信，下一步需要 P 的 kernel/通信 profile。

旧 shared L2 首轮曾出现 2.42 亿下降到 2.02 亿、manager 约 99–104% CPU 和超时。
当前 3 亿档明显改善，但 Decode 修订及运行阶段不同，**不是严格单变量 A/B**。
历史无 L2 4 亿目标的完成值约 3.233 亿；本轮 2.959 亿约为其 91.5%，
也不能将这个比率解释成精确的 L2 因果开销。

## 验证与补充运行

- 发压前共享验证 8/8：一路冷写、其余七路 HOST 各命中 40448 tokens，答案正确。
- 20/20 合成前缀预热通过。
- r1 使用原客户端节奏，实际发入仅 2.840 亿，末尾完成 2.847 亿，5134/5134 成功。
  发现 `next_send=max(next_send,now)+interval` 累积调度延迟，随后 r2 起改为绝对发送
  时间表 `next_send+=interval`，服务端代码不变。
- r1 后共享恢复验证再次 8/8；r1 最终池 held=0。
- 用户随后明确要求不排空，r3/r4 已直接终止客户端。没有将杀客户端等同于后端
  队列立即归零，也没有等待高档残余请求全部完成。
